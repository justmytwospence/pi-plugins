# Pi Plugins

This repository is the development source for the Pi extension suite. Add or change components under `packages/<name>/`, not in the retained standalone repositories or Pi's installed checkout. Keep plugins independently usable; optional sibling integrations must remain optional. The root `pi` manifest exposes distinct entry points for selection through `pi config`.

## Footer integration

When adding or changing functionality anywhere under `packages/`, read `packages/pi-status-footer/AGENTS.md`, assess footer impact, and update relevant state publications, controls, rendering, tests and public documentation in the same logical change. Those component-local instructions apply to integration work in sibling plugins; discovering them must not depend on editing the footer first. If there is no footer impact, explicitly state that assessment in the completion response.

## Checks

- Root: `npm ci`, then `npm test` for actual Pi loader selection/registration tests.
- Components: install each component's lockfile dependencies (`npm ci` in its directory), then `npm run check` there or run root `npm run check` for the full set.
- Live evals are manual and paid. Every eval is a target (`evals/shared/target.ts`): `id`, `title`, `package`, `kind` (`cases` or `replay`), `plan(ctx)` (the dry run: `{ calls, notes }`, no Jev call) and `run(ctx)` (the live run: `{ metrics, compare?, report, pass }`). It is the default export of `defineEval({...})` in `packages/<pkg>/eval/<id>.target.ts`, listed by explicit import in `evals/targets.ts` (`scripts/test-contracts.mjs` checks that every such file is listed and named after its id). One runner does the rest (`evals/shared/runner.ts`, `scripts/eval.mjs` as its CLI): `npm run -s eval -- [<id|package|all>...] [--package <pkg>] [--dry | --list | --last] [--json]`. `--list` shows the targets; `--dry` samples sessions once, calls each `plan()` and prints the calls and a spend estimate (one JSON object with `--json`; human text on stderr; `EVAL_COST_PER_CALL`, default 0.0003 USD, is a guess); `--last` prints each target's last record and its numeric diff from the run before. A live run names its targets, skips cleanly without `TYPESAFE_API_KEY`, builds the Jev registry once, runs the targets one after another, prints each report and `spend: $X over N calls` (the target adds every `askJev` outcome to `ctx.spend`), appends a record (commit, seed, `EVAL_*` params, spend, calls, `metrics`, `compare` with `EVAL_COMPARE=1`) to the git-ignored `evals/results/<id>.jsonl`, and exits non-zero when a target's `pass` is false (the Jev failure limit is 20%, `withinFailureLimit`). A package's `npm run eval` is `node ../../scripts/eval.mjs --package <pkg>`. Do not run a live eval without explicit authorization; neither `check` nor CI does; `--list` and `--dry` are free. Evals not yet ported to targets are still `eval/*.eval.ts` files run by Vitest (`evals/shared/vitest.config.ts`); `eval:dry` and `eval:last` are deprecated aliases that print the old output shape for the `/eval` extension.
- Eval helpers shared by the targets live in `evals/shared/` (target types and `defineEval`, the runner, registry, session sampler, `pool`, `table`, `spend`, `results`, and the Vitest config of the evals not yet ported). It is dev-only: not a package, never in the `pi` manifest, and `scripts/test-contracts.mjs` holds its files to Node built-ins and each other, while `eval/` files and `evals/targets.ts` may import it. A target gets the registry, the memoized session sample, `pool`, `table` and its `Spend` from its context and imports its own package's `askJev` and questions. Each package's `tsc` includes it; its unit tests (runner tests use a fake target and registry, no network) are `node:test` files that root `npm test` runs. Put a helper there once two evals need it, not a copy per package.
- Docs: `cd site && npm ci && npm run check && npm run build`. Documentation is static, separately deployed, and must not affect runtime installation.

All npm installations follow the machine's release-age policy. Never bypass it.

## Releases and installation

One Git commit/tag versions the whole suite. Components can be independently enabled, not independently Git-version-pinned from this package. Never enable both the suite copy and original standalone copy of a component. Test manifest selection, registration parity, and interactions after integration changes. A factory-loader test is not a full TUI/lifecycle test.

Publish source changes before bumping the suite pin in `~/Projects/dotfiles/home/private_dot_pi/private_agent/settings.managed.json`. Read the dotfiles chezmoi skill and `~/Projects/dotfiles/docs/plugins.md`; iterate locally as described under Live local loading, and after a pin bump let dotfiles' converge script install it (`chezmoi apply`). Never edit an installed copy. Preserve original repo history and upstream MIT attribution. `source-pins.json` records initial import provenance, not the current release versions of components.

### Live local loading

The committed `.pi/settings.json` makes every Pi session started at the root of this checkout or any of its worktrees load the suite from that checkout instead of the installed pin: its first entry is an `autoload: false` delta that disables every resource of the personal `git:github.com/justmytwospence/pi-plugins` entry, and `".."` (resolved against `<cwd>/.pi`) loads the checkout itself. Other packages are unaffected. Edit, then `/reload` in a session in that checkout to see the change; a worktree session runs its own branch. Sessions started elsewhere, or in a subdirectory such as `packages/<name>`, keep the installed pin. The checkout needs its dependencies (root and component `npm ci`). Work in progress that fails to load breaks that plugin in the session editing it: revert or fix and `/reload`, or start Pi outside the checkout. Headless subagents started here load the local code too. This is a test loop, not a rollout: everything else still updates only through the release and pin bump below.

### Completion and rollout

Unless the user explicitly requests an uncommitted change or source-only work, finishing a change includes checking it, committing its files with a conventional commit, and pushing. For runtime changes, also update the installed suite. Once the commit is on `origin/main`, cut a release: `npm run -s version:set -- <next patch>`, `npm test`, commit `chore: release <version>`, `git tag v<version>`, `git push origin main v<version>`. Tags are never moved or deleted once pushed. Then, in a dotfiles worktree (per `~/Projects/dotfiles/AGENTS.md`), set the `git:github.com/justmytwospence/pi-plugins@v<version>` spec in `~/Projects/dotfiles/home/private_dot_pi/private_agent/settings.managed.json` and the same key in `home/.chezmoidata/pi_tag_commits.json` to `git rev-parse v<version>^{commit}`, commit only those two files as `chore(pi): pin pi-plugins v<version>`, and land with `bin/land`, which applies (the converge script runs `pi update` for the new pin) and syncs the NUC. Read `~/Projects/dotfiles/AGENTS.md` and its chezmoi skill before doing so; preserve unrelated changes, including changes in the same settings file. Verify `git -C ~/.pi/agent/git/github.com/justmytwospence/pi-plugins rev-parse HEAD` equals the tag's commit on this machine and the NUC (the other Mac is not reachable; see the dotfiles policy). Do not call a runtime change done merely because its source was pushed.

Installing a new pin through the converge script writes `~/.pi/agent/reload-request`, so running sessions with pi-reload-all reload themselves once their turn ends and their editor is empty (the session doing the rollout included); a session with a draft stays pending until the draft is cleared. `/reload-all` does the same by hand on every Herdr machine. Sessions without the entry still need `/reload`. State any remaining rollout or reload step explicitly. When exactly one concrete step remains for the user, end with a `<next>…</next>` suggestion (for example, `<next>/reload</next>`); do not silently omit installation or synchronization. If rollout is blocked, report the blocker rather than claiming completion. Documentation-only changes need committing and pushing, but not a runtime pin bump.

## Remote clients

herdr-web-ui and Collie read waiting Pi dialogs off the screen. Before changing a dialog's rendering, the footer, a below-editor widget or Sidebar's layout, read `docs/clients.md` and run `npm run check:clients` afterwards. Both clients must read every screen: fix a `FAIL` or `KNOWN` line (in the suite, `frames.toml` or the Collie fork) before calling the change done; never add an exception for it.

## Documentation ownership

Do not invent external requirements or supported tools: verify source and tests. Label terminal illustrations as examples, not real screenshots.
